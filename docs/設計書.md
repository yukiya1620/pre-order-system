# 農家向け予約注文・販売管理システム 設計書

コンセプト:「誰でも迷わず使える。農家のためのやさしい予約注文システム」

作成日: 2026-07-04
バージョン: v1.0(初版・レビュー用)

---

## 1. システム概要

### 1.1 目的

高齢の農家・高齢の購入者でも迷わず使える、野菜・果物の予約注文/販売管理システムを提供する。
一般的なECサイトの多機能さよりも「見やすい・わかりやすい・操作しやすい」を最優先とする。

### 1.2 利用者と役割

| 利用者 | 役割 | 主な機能 |
|---|---|---|
| 農家(販売者) | 管理者 | 商品登録、予約管理、在庫管理、注文確認、売上管理、お知らせ配信、電話注文の代理入力 |
| 購入者 | 一般ユーザー | 商品閲覧、予約注文、注文履歴確認、配達予定確認、通知確認 |

### 1.3 前提・スコープ

- **1農家 = 1システム(シングルテナント)** で設計する。
  ※シングルテナント = 1つのシステムを1つの事業者(農家)が専有する構成。複数農家が相乗りする「モール型」は将来拡張とする。
- 対応端末: PC / スマートフォン / タブレット(レスポンシブ対応)
- 決済はスコープ外(現金・代引き等のオフライン決済を想定)。オンライン決済は将来拡張。

## 2. 技術スタック(提案)

| 分類 | 技術 | 選定理由 |
|---|---|---|
| 言語 | PHP 8.3 | Laravel との組み合わせが標準的 |
| フレームワーク | Laravel 11 | 認証・バリデーション・通知・スケジューラが標準装備で、少人数開発・少人数運用に向く |
| DB | MySQL 8.0(PostgreSQLでも可) | Laravelとの組み合わせで運用情報が最も豊富 |
| フロントエンド | Blade テンプレート + 最小限のJavaScript | SPA(※)にせず画面遷移ベースにすることで、実装も動作もシンプルになり高齢者にも安定して使いやすい |
| CSS | 自作CSS(デザイントークン方式) | 大きな文字・大きなボタンなど独自の高齢者向け基準を一元管理するため |
| 定期処理 | Laravel タスクスケジューラ + キュー(databaseドライバ) | 配達3日前通知などの定期実行に使用。Redis等の追加サーバー不要で障害点が少ない |
| 通知基盤 | Laravel Notifications | 1つの通知クラスから メール / SMS / database(アプリ内通知)へ同時配信できる |
| SMS送信 | Twilio / Vonage など外部SMS API | SMS認証・SMS通知に使用 |
| メール送信 | SendGrid など | メール通知に使用 |
| インフラ | さくらVPS / AWS Lightsail 等 + Docker | 小規模運用でコストを抑えられる |

Laravel採用の理由: 本システムは「通知」と「定期処理」が中核機能であり、いずれもLaravelの標準機能(Notifications / スケジューラ / キュー)がそのまま対応する。追加ミドルウェアなしで構成できるため、1人で運用するサービスとして保守性が高い。

※SPA(Single Page Application)= 1枚のページ内でJavaScriptが画面を書き換える方式。動きは滑らかだが実装が複雑になりやすい。本システムは「ページを移動する」従来型のほうが、高齢者にとって「戻るボタンで戻れる」など挙動が予測しやすいため採用しない。

## 3. データベース設計

### 3.1 設計の考え方(重要ポイント)

「翌年も商品を再利用できる」要件への対応:

商品を「商品マスタ」と「販売シーズン」の2つに分ける。

```
products(商品マスタ)          product_sales(販売シーズン)
「トマト」という商品そのもの      「2026年のトマト販売」の条件
├ 商品名                      ├ 価格 …………… 年ごとに変更可
├ 商品画像                    ├ 在庫数 ………… 年ごとに変更可
├ 商品説明                    ├ 販売開始日/終了日
└ カテゴリー                  ├ 配達予定日
                              └ 予約受付可否
        1つの商品に対して ──→ 販売シーズンは毎年増えていく
```

翌年は「昨年のトマト」を選んで価格と在庫を入れるだけで販売開始できる。
過去の販売実績(前年比較などの将来機能)もこの構造でそのまま集計できる。

### 3.2 ER図(テーブル関連図)

```
users ────────┬──< orders >──< order_items >──< product_sales >──< products >──< categories
(利用者)       │   (注文)        (注文明細)         (販売シーズン)       (商品マスタ)     (カテゴリー)
              │
              ├──< notifications(通知)
              │
sms_verifications(SMS認証コード)

orders ──── delivery_confirmations(配達確認)
announcements(お知らせ)※独立テーブル
```

凡例: `A ──< B` は「AひとつにBが複数(1対多)」

在庫の考え方: 現在予約数 = `initial_stock - stock_quantity`、残り予約数 = `stock_quantity`。`stock_quantity` が 0 になったら `status` を自動で `売り切れ` に更新する。

**配達予定日の決め方(`delivery_date_type`)**

- `fixed`(固定・従来通り): `orders.delivery_date` には `delivery_date_from` をそのままコピーする。収穫予約商品や、配達日があらかじめ決まっている商品向け。
- `auto`(自動計算): 注文日時と `earliest_delivery_days` / `order_deadline_time` から、システムが配達予定日を自動計算する。朝採れ野菜など、当日・翌日配達に対応する商品向け。購入者に配達日を選ばせる画面は作らない(「迷わないこと」を優先する方針のため)。計算方法は3.5節を参照。

### 3.4 在庫更新の流れ(排他制御)

同時に複数人が注文しても在庫がマイナスにならないよう、注文確定時は以下の手順で処理する。

1. トランザクション開始
2. `product_sales` の対象行を `SELECT ... FOR UPDATE` でロック(※行ロック = 処理が終わるまで他の注文を待たせる仕組み)
3. `stock_quantity >= 注文数量` を確認 → 足りなければ「申し訳ありません。売り切れました」を表示して終了
4. `stock_quantity` を減算、0 になったら `status = '売り切れ'`
5. `orders` / `order_items` を作成(配達予定日の決め方は3.5節、配達確認の即時生成は3.5節を参照)
6. コミット(確定)
7. 通知を作成(購入者:注文受付 / 農家:新規注文)

### 3.5 配達予定日の決定と配達確認の生成タイミング

生鮮食品(当日・翌日配達)と、収穫予約商品(数日後の配達)の両方に対応するため、`product_sales.delivery_date_type`によって処理を分ける。

**`delivery_date_type = 'fixed'`(固定・従来通り)**

- `orders.delivery_date` = `product_sales.delivery_date_from`
- `requires_delivery_confirmation = true`の場合、従来通り配達予定日の3日前バッチ(4.10節)で`delivery_confirmations`を生成する

**`delivery_date_type = 'auto'`(自動計算)**

注文確定時に、以下のルールで`orders.delivery_date`を自動計算する(購入者が配達日を選ぶ画面は設けない)。

- `earliest_delivery_days = 0`(当日配達可)
  - 現在時刻が`order_deadline_time`より前 → 配達予定日 = 今日
  - 現在時刻が`order_deadline_time`以降 → 配達予定日 = 明日
- `earliest_delivery_days = 1`(翌日配達)
  - 現在時刻が`order_deadline_time`より前 → 配達予定日 = 明日
  - 現在時刻が`order_deadline_time`以降 → 配達予定日 = 明後日
- 一般化すると: 基準日 = 今日 + `earliest_delivery_days`日。現在時刻が`order_deadline_time`を過ぎていれば、さらに1日後ろ倒しする。

`requires_delivery_confirmation = true`の場合、3日前バッチでは間に合わないため、**注文確定直後**(在庫排他制御と同じトランザクション内)に`delivery_confirmations`を生成し、農家へ即時通知する。

**`requires_delivery_confirmation = false`の場合**(`fixed`/`auto`共通)

`delivery_confirmations`は生成しない。通常の注文としてのみ扱う。

## 4. API設計

Laravel のAPIルート(`routes/api.php`)+ FormRequest バリデーションによるREST API。画面はBladeテンプレートで描画するが、在庫確認・再注文などの動的処理と、将来のスマホアプリ化に備えてAPIを整備する。

### 4.1 共通仕様

- ベースURL: `/api/v1/`
- 認証: Laravel Sanctum(ブラウザはセッション認証、将来のスマホアプリはトークン認証)
- 権限: farmer 専用APIは `/api/v1/farmer/` 配下に集約し、ロールで制御
- レスポンス形式: JSON
- エラー形式(統一):

```json
{
  "error": {
    "code": "OUT_OF_STOCK",
    "message": "申し訳ありません。この商品は売り切れました。"
  }
}
```

※ message はそのまま画面に表示できる「やさしい日本語」で返す。

### 4.2 認証・会員登録

| メソッド | パス | 説明 |
|---|---|---|
| POST | /auth/sms/send | SMS認証コードを送信(登録・ログイン共通) |
| POST | /auth/sms/verify | 認証コードを検証してログイン |
| POST | /auth/login | メールアドレス+パスワードでログイン |
| POST | /auth/logout | ログアウト |
| POST | /users | 会員登録(名前・電話番号・住所・メール任意) |
| GET / PUT | /users/me | 自分の登録情報の取得・変更 |

### 4.3 商品(購入者向け)

| メソッド | パス | 説明 |
|---|---|---|
| GET | /products | 販売中の商品一覧(画像・商品名・価格・予約受付状況・残り数・配達予定日・説明) |
| GET | /products/{id} | 商品詳細(配達予定日を必ず含む) |

### 4.4 商品管理(農家向け)

| メソッド | パス | 説明 |
|---|---|---|

### 4.5 注文

### 4.10 バッチ処理(Laravel タスクスケジューラ)

| 処理 | タイミング | 内容 |
|---|---|---|
| 配達確認の生成(3日後以降配達分) | 毎朝 7:00 | 配達予定日が3日後の注文(`requires_delivery_confirmation=true`)を抽出 → delivery_confirmations を作成 → 農家へ通知「○月○日に配達予定の商品があります。内容を確認してください。」※当日・翌日配達分(`delivery_date_type=auto`)は3.5節の通り注文確定直後に生成済みのため対象外 |

## 5. 画面設計(ワイヤーフレーム)

### 5.1 UIデザイン基準(全画面共通ルール)

高齢者対応の基準を数値で定義し、CSSのデザイントークン(共通変数)として一元管理する。

| 項目 | 基準 |
|---|---|
| 基本文字サイズ | 18px以上(重要な数字・金額は 22〜28px) |
| ボタン | 高さ56px以上・横幅いっぱい基調・角丸・押せることが分かる立体感 |
| タップ領域の間隔 | 12px以上(誤タップ防止) |
| 配色 | 背景は白基調。色数は3色まで(基本色・強調色・警告色) |
| 状態表示 | 色 + アイコン + 文字 の3点セット(例: 🟢●販売中 / ✕ 売り切れ)※色覚多様性対応 |
| 確認画面 | 注文・変更・削除など取り消せない操作の前に必ず表示 |
| 画面遷移 | 主要操作は トップから2タップ以内。戻るボタンを全画面左上に固定 |
| 文言 | 専門用語を使わない(「ログイン」→「はじめる」も検討。「カート」は使わず即注文方式) |

## 6. 非機能要件

| 項目 | 内容 |
|---|---|
| レスポンシブ | モバイルファースト。ブレークポイント 600px / 1024px。PCでは商品カードを2〜3列表示 |
| アクセシビリティ | WCAG 2.1 AA 相当。コントラスト比4.5:1以上、フォーカス表示、スクリーンリーダー対応のalt属性 |
| セキュリティ | HTTPS必須 / CSRF対策(Laravel標準)/ SMS認証コードは5分有効・5回失敗で無効化 / パスワードはハッシュ保存 / 個人情報へのアクセスはロールで制御 |
| 性能 | 想定規模: 購入者〜500人、商品〜100点、注文〜100件/日。一覧はページング(20件ずつ) |
| バックアップ | DBを毎日自動バックアップ(7世代保持) |
| ログ | 注文・在庫変更・配達確認の操作ログを記録(問い合わせ対応用) |
